# Version-control a personal opencode overlay (tool-proof)

- **Date:** 2026-06-26
- **Status:** Approved (design); pending implementation plan
- **Scope:** dotfiles repo (`~/.dotfiles`) — `install.sh`, `shared/.config/`,
  `shared/.zshenv.shared`, `devices/{insta-laptop,bento}/`, `tests/`. `merge-json.sh`
  is reused unchanged.

## Problem

opencode keeps its config under `~/.config/opencode/`, but almost none of that
directory is personal config worth tracking. Inventory, sorted:

| Bucket | Files | Track? |
|--------|-------|--------|
| Generated build artifacts | `node_modules/`, `package.json`, `package-lock.json`, `bun.lock` | No — opencode's own `.gitignore` already ignores them |
| Company-tool-managed | `agents/*.md`, `plugins/empty-tool-result.ts`, and the `provider` + `enabled_providers` block in `opencode.json` | No — owned/regenerated by `opencode-config` (they match the `.instacart-managed-*.json` manifests 1:1) |
| Personal / portable | in `opencode.json`: `"model": "openai/gpt-5.4"` and `"plugin": ["superpowers@git+https://github.com/obra/superpowers.git"]` | **Yes — the only real target** |
| External symlinks | `skills/*` → the separate `skillshare` repo | No — managed by skillshare tooling |

So "check in the opencode config" reduces to: **version-control two keys**, layered
so the company `opencode-config` tool cannot clobber them and so no work email or
secret enters git.

### Verified facts

- **No secrets present.** Auth flows through the Instacart AI Gateway; on-disk keys
  are literal `dummy-key`/`dummy-secret`, and there is no `auth.json` in the config
  dir. The `provider` block does, however, embed the user's work email in every
  gateway URL — a reason not to track `opencode.json` wholesale.
- **opencode config precedence** (per opencode docs): global
  `~/.config/opencode/opencode.json` → `OPENCODE_CONFIG` file → project
  `opencode.json`, deep-merged with later layers overriding earlier. **Empirically
  confirmed** on opencode `1.17.11` via `opencode debug config`: with an
  `OPENCODE_CONFIG` overlay, all six company providers survive (merge, not replace),
  the overlay's `model` overrides the global, and an identical `superpowers` plugin
  spec resolves **once** (opencode dedupes across layers — no double-load). The
  install-time `merge-json.sh` also reads through a symlinked fragment correctly
  (the `bento` case).
- **`model` and `plugin` are user-added.** Neither appears in any
  `.instacart-managed-*.json` manifest (the managed plugin is only
  `empty-tool-result.ts`). `opencode-config` therefore appears to *merge* rather than
  full-overwrite `opencode.json`, but its exact sync behavior is unverified — the
  `opencode-config` repo is not cloned locally, so this design does not depend on it.

## Decisions (from brainstorming)

- **Personal overlay only.** Not a full work-device snapshot, not an
  "everything-reproducible" tracked copy. Two keys.
- **Split by portability.** `superpowers` plugin is portable → tracked in `shared/`
  for all machines. `model: openai/gpt-5.4` only resolves through the work gateway →
  tracked in `devices/insta-laptop/` (and `bento`).
- **Compose via an extended device-layer merge** (not by duplicating the plugin line
  across two files). See Component B.
- **The overlay lives outside the tool-managed dir** and is reached via
  `OPENCODE_CONFIG`, so `opencode-config` never sees it.
- **Do not touch tool turf.** The global `opencode.json`, `agents/`, `plugins/`, and
  managed manifests are left entirely alone — zero churn, no email in git.
- **Work devices:** `insta-laptop`, `bento`. **Personal devices:** `popos`,
  `Ziyuns-M5-MacBook-Pro`, `Ziyuns-Mac-mini`, `Ziyuns-MBP`.

## Goals / Non-goals

**Goals**
- The `superpowers` plugin is version-controlled and reaches opencode on every
  machine.
- The work `model` default reaches opencode on work devices only.
- `opencode-config` can never clobber the tracked settings, and no work email or
  secret is committed.
- The plugin entry is defined exactly once (no cross-file duplication).
- A regression test fails loudly if the tool-owned `opencode.json` is ever
  symlinked into the repo.

**Non-goals**
- Tracking the generated artifacts, the managed agents/plugins/providers, or the
  `skills/` symlinks.
- Editing or disabling `opencode-config` (we route around it, as with pi-config).
- Removing the now-redundant `model`/`plugin` keys from the live tool-owned
  `opencode.json` (tool turf; left alone — see Open items for the dedup check).

## Design

### Component A — The overlay file + `OPENCODE_CONFIG`

Two tracked fragments, composed at install time into one real file that opencode
reads via `OPENCODE_CONFIG`:

- `shared/.config/opencode.personal.json` (portable base):
  ```json
  {
    "$schema": "https://opencode.ai/config.json",
    "plugin": ["superpowers@git+https://github.com/obra/superpowers.git"]
  }
  ```
- `devices/insta-laptop/.config/opencode.personal.json` (work overlay):
  ```json
  { "model": "openai/gpt-5.4" }
  ```

Both map (relative to `$HOME`) to `~/.config/opencode.personal.json` — a deliberate
**sibling** of the tool-managed `~/.config/opencode/` dir, not a file inside it. This
keeps the overlay off `opencode-config`'s turf (whose pruning behavior for unknown
files in its own dir is unverified) and avoids any chance of opencode auto-loading it
as a second global config.

`shared/.zshenv.shared` gains a guarded export (same defensive style as the existing
fzf block), so it reaches every zsh including `zsh -c`:

```sh
if [[ -f "$HOME/.config/opencode.personal.json" ]]; then
  export OPENCODE_CONFIG="$HOME/.config/opencode.personal.json"
fi
```

The file always exists after install (the shared fragment is always present), so the
guard only ever skips on never-installed machines, where `.zshenv.shared` is not
sourced anyway.

### Component B — Extend the merge to a device layer (core mechanism)

Today `install.sh` composes `.dotfiles-merge` paths as **`shared` (base) → existing
local (overlay)** with local winning (`merge-json.sh`). This adds an optional middle
layer so composition becomes:

```
shared  →  devices/<DEVICE>  →  existing-local      (later wins: local > device > shared)
```

Built from the existing binary `merge-json.sh` by chaining:
`tmp = merge(shared, device)` then `result = merge(tmp, local)`.

**Backward compatible:** when no `devices/<DEVICE>/<rel>` fragment exists (e.g. the
current `.claude/settings.json` merge), the device step is a no-op and behavior is
exactly today's `shared → local`.

Two `install.sh` changes:
1. **Defer merged paths from *every* link pass.** Move the `is_merged` deferral in
   `link_directory` out of the `check_skip` gate so it applies to the device pass too
   (currently device linking would symlink the device fragment over the merge target).
   Merged paths must never be symlinked from anywhere.
2. **Insert the device layer in the merge phase.** For each merged `rel`, compose
   `shared/<rel>` and `devices/<DEVICE>/<rel>` (each optional) and then the existing
   local file (optional), with the precedence above. Exact bash (temp files, missing
   base/overlay handling — `merge-json.sh` requires a base but tolerates a missing
   overlay) is an implementation detail for the plan.

Wiring for opencode: add `.config/opencode.personal.json` to the `.dotfiles-merge`
of `insta-laptop` and `bento` only. On those devices it is composed
(shared superpowers + device model) into a real file. On personal devices the path is
not in `.dotfiles-merge`, so normal shared-linking symlinks the portable fragment
directly → superpowers only.

### Component C — `bento` shares the work fragment (dedup)

`bento` is a work device and should get the same work `model`. To avoid drift between
the two work devices, mirror the proven Claude-overlay pattern: a repo symlink
`devices/bento/.config/opencode.personal.json -> ../../insta-laptop/.config/opencode.personal.json`,
and the same `.dotfiles-merge` entry. `merge-json.sh` reads through the symlink
transparently.

### Component D — Regression guard

Extend `tests/dotfiles_bootstrap_test.sh`:
1. Assert no path under `~/.config/opencode/` (notably the tool-owned
   `opencode.json`) ever resolves into the dotfiles repo — catches a future
   regression that would leak the work email / provider block into git. (Must not
   false-positive on the existing `skills/*` symlinks, which point at the separate
   skillshare repo, not this one.)
2. Assert the device-layer merge composes correctly: a sandboxed install for a work
   device yields `~/.config/opencode.personal.json` containing **both** `plugin`
   (from shared) and `model` (from device); a personal device yields the
   superpowers-only fragment.
3. Assert the existing `shared → local` merge (`.claude/settings.json`) is unchanged
   when no device fragment is present (backward-compat guard).

## Data flow / load order

opencode merges, low → high precedence:

```
global ~/.config/opencode/opencode.json   (opencode-config: providers, agents, plugins)
  → ~/.config/opencode.personal.json      (OUR overlay via OPENCODE_CONFIG: plugin [+ model on work])
    → project opencode.json               (per-repo, unaffected)
```

Our overlay only adds/overrides `plugin` and `model`; everything the company tool
manages flows through untouched.

## Error handling / edge cases

- **Merge precedence:** scalar conflicts resolve to the higher layer
  (local > device > shared); arrays union-dedupe — unchanged `merge-json.sh`
  semantics, surfaced via its existing stderr conflict reporting.
- **Missing fragments:** shared-only (personal device) → plain symlink; device-only
  or shared-only at merge time handled by `merge-json.sh`'s missing-overlay path.
- **Stale symlink at the merge target:** the merge phase must replace a pre-existing
  symlink at `~/.config/opencode.personal.json` with the composed real file (same
  hazard `merge_file` already handles).
- **Personal machine without opencode:** the symlinked overlay and the guarded
  `OPENCODE_CONFIG` export are harmless no-ops.

## Implementation surface

- **New tracked files:** `shared/.config/opencode.personal.json`,
  `devices/insta-laptop/.config/opencode.personal.json`,
  `devices/bento/.config/opencode.personal.json` (symlink).
- **`.dotfiles-merge`:** add `.config/opencode.personal.json` to `insta-laptop` and
  `bento`.
- **`install.sh`:** unconditional `is_merged` deferral in `link_directory`; device
  layer in the merge phase.
- **`shared/.zshenv.shared`:** guarded `OPENCODE_CONFIG` export.
- **Tests:** new assertions in `tests/dotfiles_bootstrap_test.sh`.
- **Reused unchanged:** `merge-json.sh`, device-override mechanism, `.dotfiles-merge`
  convention.

## Verification (post-implementation)

1. `DRY_RUN=1 ./install.sh insta-laptop` shows the overlay composed (not symlinked)
   and `opencode.json` never linked.
2. After a real work-device install: `~/.config/opencode.personal.json` is a regular
   file containing both `plugin` and `model`; `OPENCODE_CONFIG` points at it.
3. `DRY_RUN=1 ./install.sh Ziyuns-Mac-mini` (personal) shows the overlay symlinked to
   the shared fragment (superpowers only).
4. `opencode` picks up `model` and `superpowers` on a work device; `git status` in the
   repo stays clean across an `opencode-config` sync.
5. `tests/dotfiles_bootstrap_test.sh` passes, and fails when `opencode.json` is
   simulated as a repo symlink.
